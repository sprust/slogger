## Why

Модель не может ответить на вопросы «сколько было трейсов», «сколько из них упало», «как менялась длительность» за период: ни один инструмент MCP не считает трейсы. Проверено на живом клиенте, инсталляция `local`. В UI на это отвечает график страницы трейсов (`POST /admin-api/trace-aggregator/trace-metrics`): ряд по шагам времени с количеством и перцентилями `duration`, `memory`, `cpu` под фильтром по сервисам, типам, тегам, статусам и диапазонам. Этот график нужен модели в первую очередь.

Запрос графика строит динамический индекс. Имя индекса — набор полей фильтра и набор почасовых коллекций периода; значения фильтров в него не входят. Поэтому смена сервисов, типов, тегов и статусов при том же наборе фильтров, шаге и часах переиспользует готовый индекс. Новый индекс появляется только при новом наборе полей, новом шаге или новом часе. Отдельный бюджет индексов для такого инструмента не нужен, достаточно ограничить период и объяснить модели, как не плодить индексы.

## What Changes

- Новый инструмент `get_trace_metrics` — тот же расчёт, что у графика страницы трейсов:
  - период задаётся пресетом UI (`5 minutes` … `1 day`) и необязательным `to`, по умолчанию текущий момент; пресеты длиннее суток не принимаются;
  - шаг — один из шагов, которые UI предлагает для пресета; без шага берётся шаг по умолчанию, фиксированный для каждого пресета;
  - метрики — `count`, `duration`, `memory`, `cpu`, по умолчанию `count` и `duration`; агрегаты как в UI: сумма для `count`, `avg`, `min`, `max`, `p50`, `p95`, `p99` для остальных;
  - фильтры: `service_ids`, `types`, `tags`, `statuses`, диапазоны `duration`, `memory`, `cpu`;
  - ответ — все шаги периода по возрастанию времени, пустые шаги тоже;
  - пока индекс строится, ответ — статус `index_building` с `index_id` и подсказкой повторить тот же вызов, а не ошибка; ошибка построения индекса — ошибка инструмента.
- Инструкции сервера получают шаг с `get_trace_metrics` и правило: сравнивать сервисы, типы и статусы, меняя значения фильтров, но не их набор, шаг и период.
- Фильтр и метрики по полям `data`, `has_profiling` и `trace_ids` в инструмент не входят.
- `add-mcp-trace-queries` теряет `trace_timeseries`: его заменяет этот инструмент.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `mcp-tools`: новое требование `get_trace_metrics`. Назначение спеки расширяется: кроме инструментов без индексов, в ней описан инструмент, который строит динамический индекс трейсов, как график в UI.

## Impact

- Модули и слои Deptrac:
  - `Mcp` — `Domain/Actions/Bridges` (мост к `Trace\Domain\Actions\Queries\FindTraceTimestampsAction`), `Domain/Exceptions` (индекс строится, индекс упал), `Entities/Bridges` (результат моста), `Parameters` (аргументы запроса), `Infrastructure/Tools` (`GetTraceMetricsTool`), `Infrastructure/McpServiceProvider` (регистрация);
  - `Trace` не меняется: мост вызывает существующее действие графика и использует его перечисления `TraceTimestampPeriodEnum`, `TraceTimestampEnum`, `TraceMetricFieldEnum` и `TraceTimestampMetricsFactory::getTimestampsByDate` через действие `MakeTraceTimestampPeriodsAction`.
- Новые рёбра `Mcp → Trace` вписываются в `.ai/README.md` → Cross-Module Dependencies.
- Инструкции сервера `resources/mcp/instructions.md` и раздел MCP Server в `.ai/README.md`.
- `openspec/changes/add-mcp-trace-queries/proposal.md`: убрать `trace_timeseries`, сослаться на этот change.
- MongoDB: динамические индексы на почасовых коллекциях, не больше 25 коллекций на индекс; те же индексы использует UI, живут они 12 часов после последнего обращения.
- Admin API, OpenAPI, фронтенд и receiver не меняются.
