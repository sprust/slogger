## Why

После `add-mcp-server` модель видит отдельные трейсы по `trace_id`, но не может их найти: для этого нужны выборки и агрегаты трейсов за период. Любой такой запрос строит динамический индекс на (набор полей фильтра × почасовые коллекции периода), а модель склонна менять фильтры и расширять период. Без жёстких ограничений в коде MCP-клиент может запустить сотни построений индекса.

Изменение зависит от `add-mcp-server` и начинается после его архивации.

## What Changes

- Правило периода для всех инструментов, которые выбирают трейсы по `loggedAt`:
  - `from` и `to` обязательны, ISO 8601;
  - `from` округляется вниз до часа, `to` — вверх до часа (UTC), чтобы скользящие окна модели давали стабильный набор коллекций и переиспользовали индексы;
  - выровненный период не длиннее 24 часов; иначе ошибка инструмента `period_too_wide` с подсказкой сузить период;
  - `from` не позже `to`.
- Сервис обязателен в каждом трейсовом запросе и проверяется на существование.
- Запрет `tags` вместе с фильтром по `data` проверяется до запроса, с понятной ошибкой инструмента.
- Бюджет новых динамических индексов на одно подключение `mcps` в час (`MCP_INDEX_BUDGET_PER_HOUR`, счётчик в Redis). Считаются только индексы, которых ещё нет; для этого вычисление имени индекса выносится из `TraceDynamicIndexRepository::findOneOrCreate`, и добавляется проверка существования без создания.
- Статус `index_building` вместо ожидания: пока индекс строится, инструмент сразу отвечает статусом с `index_id`, оценкой `retry_after_seconds` и подсказкой повторить тот же вызов. Ошибка индекса — ошибка инструмента.
- Новые инструменты:
  - `get_index_status` — статус индекса по `index_id`: `building` с прогрессом, `ready`, `error`, `not_found`;
  - `list_dynamic_indexes` — существующие индексы, чтобы модель переиспользовала их;
  - `trace_facets` — типы, статусы и теги за период с количеством;
  - `trace_timeseries` — ряд количества и длительности за период; шаг подбирается так, чтобы точек было не больше 100; вместо перечисления `period` из черновика — те же `from` и `to`;
  - `find_traces` — страница трейсов за период с фильтрами и выбранными полями `data`;
  - `list_trace_data_fields` — ключи `data` трейсов типа с примерами значений.
- Промпты `investigate_errors(service, from, to)`, `investigate_latency(service, from, to, type?)`, `explain_incident(incident_id)`, `explain_trace(trace_id)`.
- Инструкции сервера получают порядок расследования с этими инструментами: широкий обзор за неделю одним вызовом невозможен, модель идёт сутками.
- Профилирование не отдаётся ни одним инструментом, в ответах трейсов нет `has_profiling`.

## Capabilities

### New Capabilities

- `mcp-trace-queries`: инструменты выборок и агрегатов трейсов за период — правило периода, проверка сервиса, бюджет индексов, статус построения индекса, ответы инструментов.
- `mcp-prompts`: промпты сервера MCP — список, аргументы, содержание.

### Modified Capabilities

- `mcp-protocol`: инструкции сервера описывают порядок расследования с трейсовыми инструментами и правило периода; `prompts/list` перестаёт быть пустым. Путь спеки появится в `openspec/specs/` после архивации `add-mcp-server`.

## Impact

- Модули и слои Deptrac:
  - `Mcp` — `Domain` (мосты, проверка периода и бюджета), `Parameters`, `Infrastructure/Tools`, `Infrastructure/Prompts`;
  - `Trace` — `Repositories` (вычисление имени индекса, проверка существования), `Domain/Actions/Queries` (при необходимости новые запросы для фасетов и ключей `data`);
  - новые рёбра `Mcp → Trace` вписываются в `.ai/README.md` → Cross-Module Dependencies.
- Redis: счётчик бюджета индексов по id подключения.
- Конфигурация: `MCP_INDEX_BUDGET_PER_HOUR`, лимиты фасетов.
- Нагрузка на MongoDB: ограничена правилом периода и бюджетом индексов.
- Черновики деталей — в истории git, коммит `b6e51180`, файл `.ai/plans/mcp-server.md`, разделы «Защита от дорогих запросов», «Ожидание индекса», «Инструменты» (уровни 1 и 2), «Промпты». Лимиты периода 7 дней и `has_profiling` оттуда не действуют.
