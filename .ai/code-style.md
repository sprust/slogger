# Оформление кода SLogger

Прямые указания пользователя в текущей задаче имеют приоритет.

### Переменные

- Не использовать сокращения в названиях переменных.
- Имена переменных с экземпляром класса должны полностью соответствовать имени класса (например, `CreateBookingHotelAction → $createBookingHotelAction`).

### Блоки

- Отделять пустыми строками все блоки `{}`.
- Разделять пустой строкой логические блоки (создание переменных, вызовы методов и т.д.).

### Комментарии

- Писать комментарии **только на английском**.
- Не писать комментарии, если их смысл очевиден в контексте.
- **Комментарий объясняет «почему», а не «что».** Что делает код — видно из кода. Комментарий нужен только там, где решение неочевидно и читатель без него сделает неверный вывод: нестандартный выбор (`strspn` вместо `ltrim`, регулярка вместо парсера), неинтуитивное поведение платформы, обход чужого бага, порядок действий, который нельзя менять.
- Не дублировать комментарием имя класса/метода и не пересказывать сигнатуру. Class-level докблок с описанием назначения не нужен, если имя класса и его публичные методы уже об этом говорят.
- Если тянет объяснить комментарием, что делает блок кода — сначала попробовать вынести его в метод с говорящим именем: это лучше комментария, потому что не расходится с кодом со временем.
- PHPDoc-аннотации (`@param`, `@return`, `@throws`) под это правило не подпадают — они несут типы для статического анализа и обязательны там, где типов в сигнатуре недостаточно.
- **Ссылку на класс или метод в комментарии оформлять через `@see`, а не упоминать имя текстом.** `@see` — это связь, по которой IDE даёт переход, поиск использований и подсветку при переименовании; имя в прозе всё это теряет и молча устаревает после первого же рефакторинга. Комментарий с ссылкой пишется докблоком (`/** … */`), потому что в однострочном `//` аннотация не разбирается:
  ```php
  /**
   * TODO: rolling this back alone breaks the app — the query forces the index by name.
   *
   * @see CalendarRepository::findOverbookingTasks()
   */
  ```
  Внутри фразы — инлайновая форма: `Actual payload is streamed via {@see CalendarResponseMaker}`. Ссылка на внешний адрес тоже идёт через `@see`: `@see https://core.telegram.org/bots/api#sendmessage`.

### Единый стиль и читаемость кода

- Перед написанием кода изучать соседние классы того же назначения и следовать их оформлению. Не писать плотный, слепленный код: разделять смысловые шаги пустыми строками, не объединять подготовку данных и несколько действий в одно выражение.
- Длина строки кода — не более 120 символов, предпочтительно до 100. Разворачивать длинные сигнатуры, вызовы, условия и выражения вертикально; не сокращать понятные имена ради ширины. Полные пути в `namespace` и `use` не разрывать.
- Избегать полностью квалифицированных имён классов в коде и PHPDoc: добавлять `use` и использовать короткое имя. При коллизии имён использовать явный `use ... as ...` с понятным алиасом.
- Правила валидации request оформлять вертикально: отдельное правило на каждой строке, как в существующих request проекта.
- Не использовать `withValidator`, если проверку можно выразить обычными правилами request. Не прятать в нём правила ради обхода генератора документации; сначала проверить существующий способ обработки этих правил.

### Параметры методов

- Именовать параметры методов, особенно если их больше одного.
- Использовать **именованные аргументы при вызове методов**, если параметров больше одного или есть хотя бы один необязательный.
- Порядок аргументов вызова обязан совпадать с порядком параметров в сигнатуре вызываемого метода или конструктора, в том числе для именованных аргументов.
- При вызове методов с именованными аргументами — располагать их **вертикально** (по одному на строку), с trailing comma.
- **Вызов функции/конструктора форматируется единообразно: либо все аргументы в одной строке, либо каждый — на отдельной строке.** Смешанный стиль запрещён — нельзя писать `new RuntimeException(sprintf(` с переносом строки сразу после `sprintf(` и аргументами вертикально. Если у вложенного вызова аргументы развёрнуты вертикально, у внешнего вызова первый аргумент тоже должен начинаться с новой строки (т.е. вложенный вызов сам становится отдельным вертикальным аргументом).
- **Исключение — единственный аргумент-массив.** Если у вызова ровно один аргумент и это литерал массива, скобки «прижимаются»: `([` остаётся на строке вызова, элементы идут вертикально, закрывается `])`. Лишний уровень отступа ради одной скобки ничего не поясняет.
  ```php
  // да
  $editAny = CustomerPermissionMiddleware::makeAny([
      new StaffPermissionGrantObject(StaffPermissionEnum::Bookings, StaffPermissionActionEnum::FullAccess),
      new StaffPermissionGrantObject(StaffPermissionEnum::Calendar, StaffPermissionActionEnum::FullAccess),
  ]);

  // нет
  $editAny = CustomerPermissionMiddleware::makeAny(
      [
          new StaffPermissionGrantObject(StaffPermissionEnum::Bookings, StaffPermissionActionEnum::FullAccess),
      ]
  );
  ```
  То же для вызова, обёрнутого в другой одноаргументный вызов: `->middleware(CustomerPermissionMiddleware::makeAny([` … `]))`.
- В **определении** метода (сигнатура) вертикальное расположение не обязательно, если длина строки не превышает 120 символов; иначе — тоже вертикально.
- Если имя одного из параметров в сигнатуре длиннее ~20 символов, оформлять сигнатуру вертикально, даже если параметр всего один.
- **Не использовать значения по умолчанию для параметров методов.** Допустимо только если **все** параметры метода имеют значения по умолчанию (полностью опциональные методы). Во всех остальных случаях вызывающий код должен явно передавать все значения — это делает контракт явным и защищает от того, что новый параметр с default-значением будет незаметно для вызывающих мест вести себя неправильно.
- Параметр `status` (а также иные поля-состояния сущности) в сигнатурах методов всегда располагать **последним** — после всех доменных/бизнес-полей. Это соответствует порядку столбцов в таблицах (`[id ... business_fields, status, timestamps]`) и делает сигнатуры предсказуемыми.
- Параметр `LocaleEnum $locale` (и иные сквозные параметры локали/представления) всегда располагать **самым последним** в списке аргументов — после всех остальных, **включая `status`**. Локаль — это сквозной параметр представления, а не бизнес-поле, поэтому её место в самом хвосте сигнатуры. Пример: `handle(int $rateId, ?HotelServiceStatusEnum $hotelServiceStatus, RateStatusEnum $status, LocaleEnum $locale)`.

### Цепочки вызовов (fluent chaining)

- В вызовах через `ActionResolver` размещать `->handle(...)` на новой строке после `->resolve(...)`; не склеивать разрешение экшена и его выполнение в длинную строку.

- **Если хотя бы одно звено fluent-цепочки разворачивается на несколько строк (аргументы вертикально), разворачивается вся цепочка**: каждый `->method(...)` начинается с новой строки, включая первый. Нельзя «приклеивать» последующий вызов к закрывающей скобке предыдущего.
- Запрещено:
  ```php
  $this->builderMaker->make(
      new FindSubRateParameters(id: $subRateId)
  )->first();
  ```
- Правильно:
  ```php
  $this->builderMaker
      ->make(
          new FindSubRateParameters(id: $subRateId)
      )
      ->first();
  ```
- Короткая цепочка целиком в одну строку (`->make($parameters)->first()`) допустима, пока ни один вызов не разворачивается вертикально и строка не превышает 120 символов.

### Массивы и условия

- Располагать ключи и значения массивов на отдельных строках.
- Пустой массив не проверять через `$arr === []`; использовать `count($arr) === 0`.
- Стараться не использовать `isset()` и `empty()`. Вместо них — явные проверки:
  - `array_key_exists('key', $arr)` для наличия ключа,
  - `=== null` / `!== null` для null,
  - `=== ''` / `!== ''` для пустой строки,
  - `count($arr) === 0` для пустого массива.
  `isset`/`empty` скрывают семантику (одновременно проверяют существование и truthy), что ведёт к неявным багам.
- В условиях со смешанными операторами (`&&` и `||` в одном выражении), а также в тернарных операторах — оборачивать группы условий в скобки, чтобы убрать неоднозначность приоритетов. Простые условия с однотипными операторами (только `&&` или только `||`) не требуют скобок: `if ($a !== null && $a > 0)` — нормально, `if ($a && $b || $c)` — нужны скобки.

### Структура классов

- Приватные и защищённые методы располагать **ниже** публичных.
- Методы реализации системных интерфейсов (например, `JsonSerializable::jsonSerialize`) располагать **в самом низу класса**, но перед деструктором (если есть).
- Деструктор в классе всегда располагать **в самом низу**.

### Порядок зависимостей в конструкторе

Зависимости в конструкторе (Action / UseCase / Service и т.п.) располагать по слоям, в порядке:

1. `ActionResolver` — всегда первым (если есть).
2. `DispatcherInterface` — сразу за `ActionResolver`.
3. Прочие сервисы/менеджеры/клиенты/конфиги/адаптеры (`*Service`, `*Manager`, `*ClientInterface`, `*ConfigInterface`, `*Adapter`, `TransactionManager` и т.п.).
4. `Repositories` — всегда последними.

Это устоявшаяся конвенция кодовой базы (см. `CreateRateAction`, `PreCalcAllAction`); единый порядок делает сигнатуры предсказуемыми.

### Порядок полей в объектах

- `[id ... status, timestamps(createdAt, updatedAt, deletedAt)]`.
- Порядок полей в DTO/Object/Parameters/сигнатурах репозиторных методов следует порядку полей источника (миграция / `@property` модели). Отсутствующие поля — пропускать, не перестраивая остальные.

### Замыкания

- Замыкание или стрелочная функция, не обращающиеся к `$this`, объявляются `static fn (...)` / `static function (...)` — в продовом коде, билдерах и тестах (включая замыкания ассертов). Статическое замыкание не захватывает объект и не держит его в памяти.
- Трогаешь файл, где соседние замыкания без `$this` не `static`, — приводить весь файл.

### Ассерты

См. также [правила тестов](skills/tests.md).

- `self::assertSame` — для скаляров (строгое сравнение типов).
- `self::assertEquals` — для массивов и nested-структур.
- **Параметры assert-методов всегда располагать вертикально** (по одному на строке) — даже если визуально влезает в одну строку. **Trailing comma НЕ ставить** — для assert-вызовов в проекте принято без неё (исключение из общего правила про trailing comma в вертикальных вызовах).
- Третий аргумент-сообщение очень полезен в DataProvider'ных тестах — без него непонятно, какой кейс упал на каком поле.

```php
self::assertEquals(
    expected: $expected->occupancies,
    actual: $actual->occupancies,
    message: "request[$i] occupancies"
);
```

### Объекты и Parameters

- Все Objects — `readonly` классы.
- Используют именованные аргументы в конструкторе.
- Всегда типизированы.
- PHPDoc для массивов: `@param array<Type> $items`.
- **Без значений по умолчанию в конструкторе.** Даже для `?type` — не ставить `= null`. Все поля обязательны, вызывающий код передаёт значение (в т.ч. `null`) явно именованным аргументом. Это делает контракт явным на каждом call site и заставляет обновлять вызовы при добавлении поля.
- Порядок полей в DTO, `*Object`-сущностях, `*Parameters` и сигнатурах репозиторных методов (`create`, `update`, `fresh`, `createOrUpdate` и т.п.) должен **следовать порядку полей источника** — таблицы/модели, для которой они создаются. Если какие-то поля отсутствуют (например, `id` в raw-DTO или `timestamps`) — просто пропускать их, не перестраивая оставшиеся. Источник — migration / `@property` docblock модели.
